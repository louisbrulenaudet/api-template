# Dependencies and uv

[`pyproject.toml`](../../../pyproject.toml) is the single source of truth for dependency declarations - do not fork any of it into ad-hoc local copies. Ruff and ty config decisions are in [`lint-and-types.md`](lint-and-types.md); Makefile targets in [`ops/makefile.md`](../ops/makefile.md).

- **Canonical lockfile is `uv.lock`**, changed only by `make lock` / `make update`.
- **Installs use `--frozen`** (`make sync`, CI, Docker): install `uv.lock` exactly, no re-resolution. This is deliberate, and it is the one tooling decision worth understanding before you change it. `exclude-newer = "7 days"` is a *relative* window, so `--locked` would re-verify the lock against a cutoff that slides every day and would eventually fail on a lock that is perfectly valid. Locking and the freshness gate happen only in `uv lock` / `make lock` / `make update`. **Trade-off:** installs therefore cannot detect a `pyproject.toml` dependency edit that was never re-locked - run `make lock` after changing dependencies.
- **`exclude-newer-package` exemptions are per-package and each needs a reason.** The global `exclude-newer = "7 days"` soak window is the default posture; the three exemptions are not blanket convenience. `httpx2` / `httpcore2` sit on the outbound critical path, so a security or performance fix has to be lockable the day it lands rather than a week later. `ruff` is dev-group-only and never enters the runtime image, so its supply-chain blast radius is categorically different from a shipped dependency. Do not exempt a runtime dependency that is not on a critical path.
- **The runtime closure is deliberately narrower than `fastapi[standard]`.** `jinja2` is dropped because nothing under `app/` renders a template and Starlette imports Jinja lazily (only `starlette.templating` touches it), so it and `markupsafe` leave the shipped image for free. That was verified by importing `app.main` and serving every route with both blocked on `sys.meta_path` - re-verify the same way before pruning anything else.
- **Nothing enforces this:** **`python-multipart` must not be pruned as "unused".** `starlette.requests` imports `starlette.formparsers` at module scope, which does a bare `import python_multipart`, so `import fastapi` itself raises `ModuleNotFoundError` without it. Neither `fastapi` nor `starlette` declares it (FastAPI lists it only under its `standard` extra), which is exactly why it is pinned explicitly here - and why grepping `app/` for it proves nothing. Prove a dependency is dead by blocking it on `sys.meta_path` and serving a request, never by grepping.
- Dev tooling (pytest, Ruff, ty, pre-commit) is the PEP 735 `[dependency-groups] dev` group, synced **by default** - no `--extra` / `--group` flag, and there are no `[project.optional-dependencies]`.
- **`fastapi-cli` lives in the `devserver` group, never in `[project] dependencies`.** Nothing in production invokes it: the Dockerfile `runtime` stage's `CMD` and `make prod` both run `uvicorn` directly, so listing the CLI as a runtime dependency would put typer / click / rich / rich-toolkit / shellingham in the shipped image for nothing. `uvicorn[standard]` is a direct runtime dependency in its own right, so it does not depend on that entry. Adding `fastapi[standard]`, or moving `fastapi-cli` back, re-ships the CLI - and re-adds `jinja2`. Its extra is `standard-no-fastapi-cloud-cli`, chosen over `standard` because it omits `fastapi-cloud-cli` and `sentry-sdk` - neither of which this template uses. CI's smoke step asserts the CLI's absence from `runtime` ([`ops/composite-actions.md`](../ops/composite-actions.md)).
- **Why `devserver` is a separate group from `dev`.** `dev` also carries `pre-commit-uv`, which depends on the **`uv` PyPI package** - a standalone installer binary. The Docker `reload` stage needs `fastapi dev` and nothing else, so it syncs `--no-dev --group devserver`; a bare `uv sync` there would put a package installer into the one image whose `runtime` parent deletes pip precisely to remove that capability, plus ruff / ty / pytest for a server that uses none of them ([`ops/dockerfile.md`](../ops/dockerfile.md)). `dev` pulls `devserver` back in via `{ include-group = "devserver" }`, and `dev` is uv's only default group, so `make dev` / `make sync` need no extra flags.
- **`requirements.txt` is a generated export of the RUNTIME closure, and `uv.lock` stays canonical.** Regenerate it with `make export-requirements` (which passes `--no-dev`) after **every** `make lock`, or the repo carries two contradictory manifests and anyone following the export installs the dev toolchain as production dependencies. Never `pip install -r requirements.txt` in the image. **`make check-requirements` enforces this and CI runs it**, so a forgotten regeneration fails the next PR instead of shipping - which matters more than tidiness, because `uv.lock` is *not* a manifest GitHub's dependency graph understands and `requirements.txt` is. That export is therefore the file Dependabot security alerts for these dependencies are computed from: stale means alerts against versions we do not ship.
- **Nothing enforces this:** **the pinned uv version has three homes and Dependabot moves only one.** The `ghcr.io/astral-sh/uv:<version>` `FROM` line in the Dockerfile (Dependabot's `docker` ecosystem), `setup-uv`'s `version:` input in `.github/workflows/ci.yml`, and `[tool.uv] required-version`. The last two are manual, so they drift silently and no check compares them. Bump all three in one change ([`ops/dependabot.md`](../ops/dependabot.md)).
- **"3.14" has four homes too:** `.python-version` (which CI reads via `python-version-file`), `[project] requires-python`, Ruff's `target-version`, and the Dockerfile base tag. Move them together.
