# Dockerfile and build context

Validated against Docker's [build best practices](https://docs.docker.com/build/building/best-practices/), [build checks](https://docs.docker.com/build/checks/) and the [uv Docker guide](https://docs.astral.sh/uv/guides/integration/docker/). Read the [`Dockerfile`](../../../Dockerfile) and [`.dockerignore`](../../../.dockerignore) for what they currently do; this rule covers the decisions behind them and the traps that are not visible in the files. Compose is a separate concern ([`ops/compose.md`](compose.md)) - Compose builds only the `reload` stage and describes local development, never production.

## Build context

`.dockerignore` is an **allowlist**: it excludes everything (`*`), then re-includes only what the Dockerfile copies. So **adding a `COPY <path>` means adding the matching `!<path>` in the same change**, or the build fails on a missing file. Re-exclude caches even inside allowlisted trees (`app/**/__pycache__`, `*.pyc`).

**The blanket guarantee stops at `!app/**`.** That pattern re-includes *everything* under `app/`, so a stray `app/.env` or `app/service.key` would land in the image. The explicit re-exclusions for `.env*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.keystore` under `app/` put it back.

**Nothing enforces this:** do not narrow `!app/**` to `*.py` instead. `app/` holds only Python today, so that pattern would look equivalent and pass CI, then silently drop the first data file anyone adds - and a missing asset fails at *request* time, not build time. Re-exclude by what must stay out, never by allowing only one extension.

**`.dockerignore` does not read `.gitignore`**, so gitignored-but-present files are *not* covered by that re-exclusion list unless it names them. `app/.DS_Store` was the worked example: gitignored, present on any macOS checkout, re-included by `!app/**`, and therefore shipped in the image - where it discloses a directory listing including the names of files since deleted. Hence the `app/**/.DS_Store`, `._*`, `.AppleDouble` and `.Spotlight-V100` entries. Add editor/OS metadata here, not to `.gitignore`, when the concern is the image.

## Image build

- **`# check=error=true`** turns Docker's build-check warnings into build failures, so `docker build` cannot succeed with a lint-level defect. `# syntax=docker/dockerfile:1` is deliberately unpinned at the minor level because the `check` directive needs frontend ≥ 1.8. `make docker-check-build` (`docker build --check`) runs the rules *without* executing build steps; CI runs it as a fast pre-gate.
- **Multi-stage, and `uv` never reaches `runtime`.** It lives in `builder`; `runtime` copies the finished `/app/.venv` only, which is both smaller and less attack surface. `COPY --link` improves cross-build cache reuse.
- **`builder-dev` exists so the dev toolchain never reaches `runtime`.** `fastapi-cli` is dev-only ([`quality/uv-dependencies.md`](../quality/uv-dependencies.md)) because `runtime`'s `CMD` runs `uvicorn` directly, so shipping the CLI would put typer/click/rich in production for nothing. `builder-dev` derives from `builder` and re-syncs with **`--no-dev --group devserver`, never a bare `uv sync`**: the full `dev` group pulls `pre-commit-uv`, which depends on the `uv` PyPI package - a standalone installer binary - so widening this would hand a package installer to the one image whose `runtime` parent just deleted pip to take one away, and drag ruff / ty / pytest in behind it. That is why `devserver` is its own group. `reload` then overlays that venv with a **plain `COPY`, deliberately not `--link`**. The union is safe only because both venvs came from the same `uv.lock`, so every shared package is identical and the overlay purely adds files. `--link` writes an independent layer that does not build on the previous state - right for the venv in `runtime`, wrong for an overlay. `COPY` also runs as root regardless of the inherited `USER`, so ownership stays consistent without juggling it.
- **The base ref is written once, as a literal, in an alias stage** (`FROM python:3.14-slim-trixie AS base`; `builder` and `runtime` both do `FROM base`). An alias stage costs nothing and keeps the two stages from drifting. It is deliberately **not** `ARG PYTHON_IMAGE` + `FROM ${PYTHON_IMAGE}`: Dependabot's Docker parser matches only a literal reference on a `FROM` line and has no `ARG` resolution (dependabot-core `docker/lib/dependabot/docker/file_parser.rb`, `FROM_LINE`), so the indirection would make every base image invisible to it. Change the version by editing the `FROM`.
- **The Debian codename is part of the pin.** Use `3.14-slim-trixie`, not `3.14-slim`: both `slim-bookworm` and `slim-trixie` exist upstream, so the suite-less tag is an **alias** that gets repointed at the next Debian stable - an OS major upgrade arriving silently under an unchanged tag. Naming the codename turns it into a reviewable Dependabot PR instead.
- **Pin bases by version *and* digest** (`tag@sha256:…`) - a tag is not an immutability guarantee, because tags can be moved across commits ([uv Docker guide](https://docs.astral.sh/uv/guides/integration/docker/)). Keep the tag alongside the digest: that is the form Dependabot's `docker` / `docker-compose` ecosystems update, and they bump both together ([`ops/dependabot.md`](dependabot.md)). Resolve one with `docker buildx imagetools inspect <ref> --format '{{.Manifest.Digest}}'` - that returns the multi-arch **manifest-list** digest, which is the one to pin; an architecture-specific digest breaks the build on another platform. The uv image also publishes GitHub attestations, so its provenance can be checked one-off with `gh attestation verify --owner astral-sh oci://ghcr.io/astral-sh/uv:<version>`. `.github/actions/verify-base-digests` asserts the index property on every PR ([`ops/composite-actions.md`](composite-actions.md)).
- **`pip` is stripped from `runtime`.** `python:*-slim` ships it in the *system* site-packages, but the venv uv builds has neither pip nor setuptools and `PATH` resolves the venv first, so nothing can reach it - it is pure advisory surface plus a package-install vector inside a compromised container. Removed with `rm -rf` rather than `pip uninstall`, because by that point bare `python3` *is* the venv interpreter and has no pip module, and because `rm -rf` is idempotent and so cannot break a future base image that already omits pip. That costs a hardcoded `python3.14` in the paths, which moves with the `FROM` tag anyway; the smoke test's assertion against `/usr/local/bin/python3` is what stops the removal degrading into a silent no-op if the layout ever changes. **Three paths, not one:** `ensurepip/_bundled` has to go too or `python -m ensurepip` simply puts pip back, and `pip-*.dist-info` has to go because that metadata is what CVE scanners read - leaving it behind means a `find_spec`-style check calls a dirty image clean.
- **`app/` is byte-compiled in `runtime`** (`python -m compileall -q /app/app`). `UV_COMPILE_BYTECODE=1` only covers site-packages; `app/` arrives as plain source, so without this its modules are recompiled on every cold start and `PYTHONDONTWRITEBYTECODE=1` discards the result each time. `compileall` writes `.pyc` regardless of that variable - this is the one place the two settings cooperate. It must stay **before `USER`** so the bytecode is root-owned, and a non-zero exit on a syntax error makes it a free build-time gate. **Leave the invalidation mode at the default `timestamp`**: a timestamp `.pyc` records the source's mtime *and* size and import compares both, so an edit synced into `reload` by Compose `develop.watch` invalidates it correctly. `unchecked-hash` is marginally cheaper but skips validation entirely, which is wrong for that stage; `checked-hash` is also safe but re-reads and hashes every source on every import, paying I/O forever against a race timestamps already cover.
- **`--frozen`, not `--locked`** - see [`quality/uv-dependencies.md`](../quality/uv-dependencies.md) for why the relative `exclude-newer` window makes `--locked` drift.
- **`UV_LINK_MODE=copy` is required**, not a preference: the cache mount is a different filesystem, so hardlinking fails. `UV_PYTHON_DOWNLOADS=0` uses the base image's Python. `[tool.uv] package = false` means `uv sync` installs dependencies only, so `app/` is copied separately as source.
- **Non-root with a fixed UID**, `USER` set before `CMD`. Keep `PYTHONDONTWRITEBYTECODE=1` so a read-only rootfs never tries to write `.pyc`. The other two runtime `ENV`s are not decoration either: `PYTHONUNBUFFERED=1` is what makes output visible in `docker logs`, and `PYTHONHASHSEED=random` mitigates hash-flooding.
- **`FORWARDED_ALLOW_IPS` must name the peers allowed to set `X-Forwarded-For` / `X-Forwarded-Proto`.** uvicorn enables `--proxy-headers` by default but trusts only `127.0.0.1`, and a sidecar proxy (the `cloudflared` service) connects from another container on the bridge network - so forwarded headers were silently discarded. The whole failure chain followed from that one default: `request.client.host` became the proxy's IP, `FORCE_HTTPS` produced an infinite redirect loop because `scope["scheme"]` stayed `"http"`, and that in turn kept the `HEALTHCHECK` failing, so the tunnel's `depends_on: service_healthy` never released. **Nothing enforces this:** set it to RFC1918 CIDRs and **not `"*"`** - a wildcard is still *correct* behind a container-network proxy and every test still passes, but a directly published port then accepts spoofed client IPs and scheme from the internet. It is an env var rather than a `--forwarded-allow-ips` flag precisely so a deployment can override it without a rebuild - uvicorn reads the variable only when the flag is absent, so do not add the flag. `make prod` deliberately leaves it unset ([`ops/makefile.md`](makefile.md)).
- **Exec-form (JSON-array) `CMD`** so the server is PID 1 and actually receives SIGTERM. Shell form silently breaks graceful shutdown. `--no-server-header` is on it deliberately: the `server: uvicorn` banner only tells a scanner what to target.
- Keep the OCI labels (`org.opencontainers.image.*`) for provenance, and keep them **late in the stage** - a `LABEL` layer above the venv/source copies would bust them on every metadata change. CI injects `APP_VERSION`; see [`ops/ci.md`](ci.md) for why both builds must pass the same value.

## Base image: a settled decision

`python:3.14-slim-trixie` is chosen, not accidental. **Do not re-open it without new information**, and do not switch quietly - the four alternatives below were each rejected for a concrete reason.

- **Alpine** - musl's allocator and DNS resolver differ from glibc in ways that are the wrong risk on an API request path, and it breaks `groupadd`/`useradd` in `runtime`. Its low CVE count is largely an artifact of a narrower advisory database, not of less reachable code. **If a scanner suggests it, take the patch by bumping the `slim-trixie` digest instead** - a runtime-version signal is orthogonal to libc, and the tags such tools suggest (`alpine`, `3-alpine`, `3.14-alpine`) are floating aliases that violate the tag+digest pin above.
- **`gcr.io/distroless/python3`** - tracks Debian's *system* python3, not 3.14, so it cannot serve this app at all.
- **Chainguard** - free tier publishes only `:latest`, so a real 3.14 pin needs a paid subscription; its fixed `nonroot` UID 65532 also collides with the UID 10001 convention and the smoke test's `expected-uid`.
- **Hand-rolled distroless** - best size and CVE numbers, but contradicts `UV_PYTHON_DOWNLOADS=0` and is fragile across Python bumps.

## Healthchecks

Each servable stage's `HEALTHCHECK` must target the port **that stage** serves. `runtime` serves 8001 and `reload` serves 8000, so `reload` has to **override** the inherited check - a stage that changes the port but keeps the parent's check reports unhealthy forever. `--start-interval` speeds up start-period detection and needs Engine ≥ 25.0. A Compose `healthcheck` replaces the image's wholesale, flags included ([`ops/compose.md`](compose.md)).

**Exec form here too**, and a Python probe rather than `curl`/`wget`: no `/bin/sh` is spawned per probe, and it survives a shell-less base if `runtime` is ever swapped for distroless. A probe must never reach a downstream dependency, or this container reports unhealthy for someone else's outage.

## Graceful shutdown

`--timeout-graceful-shutdown` has **no default in uvicorn**: without it the server waits on in-flight requests indefinitely, whatever stop window the orchestrator applies expires, and SIGKILL truncates them. **Keep the uvicorn timeout strictly below that window.** It is 25s in the `runtime` stage's `CMD`, which fits inside Kubernetes' `terminationGracePeriodSeconds` (default 30s) and CI's `docker stop --timeout 30`. Raising one without the other silently reintroduces the truncation.

This pairing does **not** involve `compose.yaml`, which builds a different stage with no in-flight-request budget to protect ([`ops/compose.md`](compose.md)).

## Secrets

Duplicated in [`ops/compose.md`](compose.md) on purpose rather than cross-referenced: a path rule is not re-injected after `/compact`, so a reader who opened only `compose.yaml` would otherwise be wiring credentials with these invariants absent.

**Nothing enforces this:** never put secrets in `ENV` / `ARG`. They persist in image layers and in `docker history`, so the leak outlives the build and no gate in this repo fails - `assert-no-baked-credentials` catches the shapes it knows, not every one. Use `RUN --mount=type=secret,id=…` at build time, and Compose `secrets:` / `env_file` at runtime. **Never `COPY .env`.**
